# 即梦 / Dreamina 视频水印去除：完整技术记录

本文记录把「即梦（Jimeng / Dreamina）视频水印」去掉的全过程，包括踩过的坑、
失败的尝试、最终成立的算法，以及可复用的经验。凡是数字都是本机实测，不含推测。

- 测试素材：`jimeng.mp4`，1280×720，24 fps，393 帧，16.375 秒
- 硬件：Tesla V100-PCIE-32GB（Volta / sm_70），驱动 573.96
- 环境：Python 3.12.14，`onnxruntime-gpu==1.19.2`，`nvidia-cudnn-cu12==9.10.2.21`
- 上游：`remove-ai-watermarks v0.60.0`

---

## 1. 问题的本质：不是参数不对，是水印会移动

最初的现象是「用 cv2 去水印，发现即梦的左下角和右上角水印没去掉」。

第一反应容易误判为「视频有旋转元数据，坐标系错位」。**这个假设是错的**：
用 ffprobe 检查该视频 `width=1280 height=720 sample_aspect_ratio=1:1`，
没有 `rotation` / `displaymatrix` 字段。画面方向完全正常。

真正的规律，是靠「时间中位数」把静态叠加从运动背景里分离出来之后才看清的：

| 时段 | 左上 | 右上 | 左下 | 右下 |
| --- | --- | --- | --- | --- |
| 0–4s | AI生成药丸 | — | — | **即梦 logo + @昵称** |
| 4–8s | AI生成药丸 | — | **即梦 logo + @昵称** | — |
| 8–12s | AI生成药丸 | **即梦 logo + @昵称** | — | — |
| 12–16.4s | 黑场淡出，无叠加 | — | — | — |

两条结论：

1. **「AI生成」药丸是整片常驻的**（中国 AIGC 标识要求），位置固定在左上。
2. **「即梦」logo + @昵称每 4 秒换一个角**，顺序是右下 → 左下 → 右上。

所以任何「写死一个角」的预设都必然漏擦 2/3 的时间。这是设计层面的问题，
不是调参能解决的。

> 12 秒后检测不到水印是**正确的**：第 289 帧亮度骤降到 0（黑场淡出开始），
> 末段亮度均值只有 13.7。不是检测失败。

## 2. 上游为什么不支持即梦

上游仓库的 `remove-ai-watermarks/docs/module-internals.md` 明确记录该水印被 **PARKED**：

> 即梦 CN 水印在视频上模板匹配分不开正负样本（1/5 正样本 vs 2/25 负样本），
> 左上「AI生成」药丸的误报模式是静态纹理角，时间递归仲裁器无法拦截。

上游视频可见水印检测表只注册了 8 个厂商：
`sora / veo / seedance / doubao / dola / hailuo / vidu / kling`。

即梦在**图片**注册表里反而有 `jimeng` / `jimeng_pill` 条目
（`jimeng_engine.py`，用 `assets/jimeng_alpha.png` 做形状匹配，
阈值 0.45 能干净分开）。图片能做的原因是：静态图没有「运动背景」干扰，
模板匹配的正负样本可分。

**教训**：不要试图去“修”上游的检测器。视频上的模板匹配受运动背景影响太大，
这个方向已经被验证过不可行。正确做法是绕开检测、直接给定区域。

## 3. 关键工具：时间中位数图

这是整个方案的基础技巧，值得单独记下来。

### 原理

水印是**静态叠加**——同一块像素在整段内几乎不变。
运动背景在每一帧都不同。于是：

```python
# 对一段内的 N 帧求逐像素中位数
stack = np.stack([frame[i] for i in range(start, end)])
median_img = np.median(stack, axis=0).astype(np.uint8)
```

中位数会把运动背景「平均」成模糊的中间色调，而**静态叠加的水印会被完整保留**。

### 效果

对 0–4s 段求中位数后，右下角能清晰看到完整的「即梦」二字 + 箭头 + @昵称，
背景则是糊掉的地面。这一步之后才有办法做几何分析。

### 采样不必全帧

一开始每段用了 10–12 个采样帧（而非全部 24/96 帧），中位数结果完全够用，
速度快一个数量级。`samples_per_chunk=10` 是实测够用的值。

## 4. 走过的弯路（都失败了）

记录下来避免以后重复踩。

### 4.1 边缘能量扫描 —— 失败

思路：水印是锐利矢量叠加，Sobel 梯度均值会明显高于周围背景。

结果：**完全被背景干扰**。0–4s 段右下边缘能量 75.6，而 4–8s 段右下（无水印）
仍有 60.5——因为背景里有纹理。比值只有 1.3 倍，不足以判定。

### 4.2 白色像素占比 —— 失败

思路：即梦 logo 和文字都是白色，统计 `V>185 & S<70` 的像素占比即可。

结果更糟：**误报区比水印区还高**。

| 区域 | 白色像素占比 |
| --- | --- |
| 真正的水印（4–8s 左下 logo） | 10.95% |
| 误报（4–8s 右下，白色衣物） | 9.01% |
| 真正的水印（0–4s 右下 logo） | 8.72% |

关键发现：**背景里只要有白色物体（衣服、墙、地面高光），白色判据就失效**。

### 4.3 整段静态像素连通域 —— 失败

思路：`|帧 - 中位数|.mean() < 6` 的像素算「几乎不随时间变化」，再做连通域。

结果：**整块区域都被判为静态**。0–4s 段静态像素 100123 个，
联合包围盒就是整个搜索窗 `(742,475,538,245)`。原因是摄像机运动缓慢时，
大块背景也近似静止。

### 4.4 时间持久性按列扫描 —— 部分可用但不可靠

思路：静态水印的每一列在整段内都是白的，运动背景不会停在同一条列上。

实测：在右上角（背景纯净）有效，框内 ratio 0.125 而背景只有 0.011，区分度 11 倍。
但在右下/左下（背景有白色物体）失效：远处背景 `p99` 也达到 1.0。

**结论：持久性可以用于「验证」，但不能用于「定位」。**

### 4.5 单模板匹配追踪 logo —— 失败

思路：从 0.0s 右下角截取 logo 做模板，全片 `matchTemplate` 追踪位置。

结果：**只匹配到右下角**（0–4s，96 帧，score 0.85~1.0）。
换到左下、右上时 score 掉到 0.3~0.5，因为模板里带了地面纹理，
而不同角的背景完全不同。多尺度（0.8~1.25）也救不回来。

## 5. 最终方案：字形结构 + 长度自适应

成功的判据不是「白色」，也不是「边缘能量」，而是**规整的文字排版结构**。

### 5.1 核心洞察

「即梦」logo 的版式是固定的：

```
[箭头] 即 梦          ← 同一字号，高度一致，横向相邻
       @昵称          ← 下一行，字号更小
```

这种「两行文字、上行两个字高度几乎相等、下行左对齐」的排版，
在自然画面里**极罕见**。用它做判据，误报率远低于纯颜色/纯边缘。

实测三个角的字形高度比（`max(h)/min(h)`）：

| 角 | wordmark 两字高度比 |
| --- | --- |
| 右下 | 1.00 |
| 左下 | 1.07 |
| 右上 | 1.00 |

而背景里的假候选通常在 1.15~1.5 之间。阈值取 **1.15** 能干净分开。

### 5.2 定位流程

```python
# 1) 分块 + 时间中位数
for chunk in chunks(1 秒):
    median = np.median(sampled_frames, axis=0)

# 2) 找白色字形连通域
glyphs = 白色连通域(median, V>178, S<90, area>=110, fill>=0.13)

# 3) 找「即梦」：高度一致 + 横向相邻
wordmark = 两个 h>=18 且 h比<=1.15 且 gap<=1.2*h 的字形

# 4) 向下找 @昵称行（宽度自适应）
nickname = 落在 wordmark 下方、高度 10~1.15*h、水平连成一片的字形

# 5) 左扩箭头（彩色，不在白色掩码里）
x1 = wordmark.x1 - round(h * 1.9)
```

### 5.2.1 中文笔画会断裂成多块（重要陷阱）

「即梦」两个字在白色掩码里**不是两个连通域，可能是三到四块**：

| 块 | 绝对 x | 尺寸 | 属于 |
| --- | --- | --- | --- |
| 1 | 117 | 20×30 | 「即」的左半（视字旁） |
| 2 | 138 | 18×28 | 「即」的右半（卩） |
| 3 | 160 | 35×28 | 「梦」整体 |

旧实现「取同高度的前两块」会把第 3 块整个丢掉，框右边界停在 156，
而「梦」实际延伸到 196 —— **残留就是这么来的**。

正确做法：收集**同一行、高度一致、横向连续的全部字形**。
判据用「与组内高度中位数的偏差 ≤ 20%」而不是「只取前两块」：

```python
h_med = np.median([g["h"] for g in group])
kept = [g for g in group if abs(g["h"] - h_med) / h_med <= 0.20]
# 再按跨度约束：从最左字形起，3 倍字高以内都算同一个词标
reach = max(g["h"] for g in kept) * 3.0
kept = [g for g in kept if g["x"] - kept[0]["x"] <= reach]
```

**经验**：凡是「按数量取前 N 个」的规则，遇到中文都可能出错。
应该按**几何连续性**收集，数量交给数据决定。

### 5.2.2 必须留安全余量

即使框已覆盖所有字形，右/下紧贴笔画边缘仍会残留——因为字形最外侧
一列的抗锯齿像素亮度低于白色阈值（`V>178`），检测不到，但擦除时
那部分像素没被掩码覆盖。

实测左下角修复后右侧只剩 **2px** 余量，仍有残影。
现在右、下各加 `max(3, 0.18 × 字高)` 的余量。
半字高范围内都是纯背景，多擦这一点没有观感损失。

### 5.3 箭头为什么单独处理

「即梦」的箭头是**渐变色**（橙→粉→紫），不在白色掩码里。
它也不适合用颜色定位——实测饱和度阈值扫过 110，右上角箭头所在列的
持久性覆盖率仍接近 0（信号太弱）。

改用几何关系：箭头相对首字左边缘的距离是**固定设计**，只随缩放变化。
三个角实测所需比值：

| 角 | 首字x | 字高 | 箭头x | (首字-箭头)/字高 |
| --- | --- | --- | --- | --- |
| 右下 | 1121 | 28 | 1094 | **0.96** |
| 左下 | 117 | 30 | 62 | **1.83** |
| 右上 | 1137 | 27 | 1094 | **1.59** |

取上限 **1.9**（留余量），三个角全部覆盖。

### 5.4 @昵称长度自适应（关键需求）

这是用户明确提出的一点：`@娥酱` 只是本视频的作者名，实际会变成
`@张三`、`@李思思思思` 等，长度完全不同。

**绝对不能写死宽度。** 实测发现昵称行甚至比 logo 本身还宽：

```
logo「即梦」  : x=1137..1176  (39px)
@娥酱 一行    : x=1142..1202  (60px)  ← 比 logo 更宽
```

所以框宽取 `min(wordmark.x1, nickname.x1)` 到 `max(wordmark.x2, nickname.x2)`，
完全由检测结果决定。

合成图定量验证（背景纯灰，2 字 → 20 字）：

| 昵称字数 | 框宽 |
| --- | --- |
| 2 | 108 px |
| 5 | 183 px |
| 8 | 258 px |
| 12 | 358 px |
| 20 | 358 px（受测试画布宽度限制，非算法问题） |

严格线性增长，每字约 25px（字宽 17 + 间距 8）。

### 5.5 搜索窗口要够宽

最初窗口取 42% 帧宽，长昵称会被窗口右边界截断（框宽卡在 198px 不动）。
改为 **55% 宽 × 34% 高** 后解决。

## 6. 检测退化与时间平滑

逐块检测会因背景变化出现个别块漏检（实测 6–7s、2–3s、10–11s）。
如果不处理，一段水印会被切成多个时段，行为不一致。

### 6.1 退化框过滤

某些块会把**昵称行的小字**误判成 wordmark，得到一个只有 25px 高的扁框
（如 `(379,125,81,25)`）。判据：

```python
# 真正的水印框必须同时包含 wordmark 行与昵称行，
# 高度约为字高的 1.7 倍以上
if nickname and (full.y2 - wordmark.y1) < wordmark.h * 1.7:
    return None   # 视为退化，丢弃
```

### 6.2 短空档合并

```python
# 空档很短，且空档之后第一个命中仍是同一个角 -> 说明没换角，只是漏检
if prev.corner == current.corner and gap_frames <= fps * 1.2:
    merge_into(prev, current)
```

### 6.3 长空档兜底

长空档（如黑场淡出、转场）检测不到 logo，但为了防转场残影，
把**所有已知角**都擦一遍。这是「宁可多擦」的保守策略。

## 7. 逐帧区域：擦除引擎的改造

上游 `_mask_for_region` 接受单个区域，一次前向处理。

即梦需要**不同帧用不同区域**，所以 `erase_video_regions()` 的 `regions`
参数扩展为两种形态：

```python
# 静态：手动画框、单点预设
regions = [(6, 8, 80, 40), (1064, 551, 138, 75)]

# 逐帧：即梦四角轮换
regions = [
    [(1064, 551, 138, 75), (6, 8, 80, 40)],   # 第 0 帧
    ...
]
```

类型判别：`isinstance(regions[0], list)`。

**性能要点**：一帧内的所有区域先合并成一个掩码，再调用一次 `fill()`。
多区域合并为一次前向，比每区域一次快近一倍（2.18s → 1.09s/帧）。

MI-GAN 内部会按掩码包围盒裁剪（`_padded_crop_box`，`pad_frac=2.0, pad_min=256`），
所以区域略微放大不会显著增加计算量——但**定位不准会直接漏擦**。

## 8. 验证方法：怎么证明「真的擦掉了」

肉眼看截图不可靠，尤其背景复杂时。改用**量化指标**：

### 8.1 文字笔画能量

```python
lap = cv2.Laplacian(gray_crop, cv2.CV_32F, ksize=3)
energy = np.abs(lap).mean()
```

锐利的文字边缘会产生高拉普拉斯响应，平滑背景则接近 0。
对同一区域比较原始与输出即可。

实测（cv2 后端，393 帧）：

| 区域 | 原始 | 处理后 | 降幅 |
| --- | --- | --- | --- |
| 0-4s 右下 | 148.67 | 6.27 | **95.8%** |
| 4-8s 左下 | 144.27 | 6.39 | **95.6%** |
| 8-12s 右上 | 138.16 | 6.08 | **95.6%** |
| 左上药丸 | 112.80 | 6.57 | **94.2%** |

### 8.1.1 指标陷阱：拉普拉斯能量会冤枉 MI-GAN

用「文字笔画能量」（拉普拉斯绝对值均值）验证擦除效果时，必须结合后端类型看：

| 后端 | 填充区能量 | 同帧真实背景能量 | 比值 | 白像素清除率 |
| --- | --- | --- | --- | --- |
| **MI-GAN** | 39~45 | 58~69 | **0.61x** | 94.5%~97.4% |
| **cv2** | 6.1~6.4 | 58~69 | **0.09x** | **100%** |

同一段水印（原始能量 126~148），MI-GAN 处理后只剩 70% 降幅，
cv2 却有 95%+。**这看起来像 MI-GAN 有残留，其实是误判**：

- cv2 的 inpaint 会生成**平滑模糊**（能量掉到背景的 9%），数值漂亮但视觉上会「糊」
- MI-GAN **生成合理纹理**（能量是背景的 61%），数值「难看」但视觉更自然

判断有没有残留，**不能只看能量降幅**，要看：

1. **白像素是否归零**（水印是白色文字，这是硬指标）
2. **填充区能量是否显著高于周围背景**（残留水印会高出数倍）

MI-GAN 的 0.61x 说明它比背景略平滑，属于正常生成纹理；
若出现 3x、5x 这种，才是水印残留。

**教训**：验证指标要匹配被测量的对象。「锐利度」适合判断文字是否存在，
但不适合评价生成式模型的填充质量——它天生会带来新纹理。

### 8.2 对照组：不该变的角

同一份输出，检查「当时没有水印的角」是否几乎没变：

| 区域 | 原始 | 处理后 | 变化 |
| --- | --- | --- | --- |
| 0-4s 左下（无） | 51.39 | 51.80 | +0.8% |
| 0-4s 右上（无） | 42.79 | 43.46 | +1.6% |
| 4-8s 右下（无） | 60.51 | 60.82 | +0.5% |
| 4-8s 右上（无） | 38.77 | 39.80 | +2.7% |

**找不到这个对照组，就不能声称「没有误伤」。**

### 8.3 全片质量

| 指标 | 值 |
| --- | --- |
| 全帧 PSNR | 30.61 dB |
| 平均改动像素占比 | 1.01% |

改动像素占比 1.01% 与水印面积量级吻合——证明只动了该动的地方。

### 8.4 药丸要用别的判据

「AI生成」药丸是**半透明白底 + 深色字**，不是纯白，白色判据抓不到。
改用「药丸区域内部的亮度标准差」：药丸存在时有文字结构，标准差高；
擦干净后变成平滑背景，标准差骤降。

| 时段 | 原始标准差 | 处理后 |
| --- | --- | --- |
| 0-4s | 34.44 | 18.68 |
| 4-8s | 34.99 | 18.99 |
| 8-12s | 27.96 | **7.34** |

## 9. GPU 加速：V100 的血泪史

这部分与即梦无关，但同样是踩了很多坑才跑通，一并记录。

### 9.1 症状

装好 `onnxruntime-gpu` 后 `CUDAExecutionProvider` 出现在 provider 列表里，
但一推理就报：

```
cudaErrorNoKernelImageForDevice: no kernel image is available for execution on the device
```

### 9.2 根因

**V100 是 Volta 架构，计算能力 sm_70。官方 onnxruntime-gpu 从 1.20 起移除了
sm_70 的 kernel。**

版本矩阵实测：

| onnxruntime-gpu | cuDNN | 结果 |
| --- | --- | --- |
| 1.31.1 | 9.x | ❌ 需要 CUDA 13（`cublasLt64_13.dll` 缺失） |
| 1.22.0 | 9.x | ❌ `cudaErrorNoKernelImageForDevice` |
| 1.21.1 | 9.x | ❌ `cudaErrorNoKernelImageForDevice` |
| 1.19.2 | 9.28 | ❌ `CUDNN_STATUS_EXECUTION_FAILED_CUDART` |
| **1.19.2** | **9.10.2.21** | ✅ **可用** |

关键点：**cuDNN 9.10 是最后一个仍支持 Volta 的版本**（9.12+ 放弃），
而 **ORT 1.19.2 是最后一个仍带 sm_70 kernel 的版本**。两者必须同时锁定。

### 9.3 Windows DLL 搜索路径

pip 装的 CUDA/cuDNN DLL 在 `site-packages/nvidia/*/bin`，
Windows **不会**自动搜索这些目录，报：

```
Error 126 "..." which is missing
```

必须在 `import onnxruntime` **之前**：

```python
for bin_dir in (Path(sys.prefix) / "Lib/site-packages/nvidia").glob("*/bin"):
    os.add_dll_directory(str(bin_dir))
```

注意 `add_dll_directory` 的句柄必须保持存活（不要放进会被回收的临时变量）。

### 9.4 还缺 cuFFT

补齐 `cublas` + `cudnn` 之后，还报缺 `cufft64_11.dll`。
说明 ORT 1.19.2 的 CUDA provider 依赖 cuFFT。装上 `nvidia-cufft-cu12` 才通过。

**排查方法**：每次报错只提示一个缺失 DLL，需要逐个补齐、逐个重试。
不要假设装完 cuDNN 就够。

### 9.5 Windows 下启动补丁的正确位置

上游 `region_eraser._get_session()` 把 provider 写死为 `["CPUExecutionProvider"]`。
**不要改上游源码**——`uv sync` 会覆盖。

改为进程内猴子补丁：

```python
original = region_eraser._get_session
region_eraser._get_session = wrapped_factory
```

## 10. 性能陷阱：时间一致性是最大瓶颈

上游默认开启 `temporal_consistency=True`（光流平滑）。实测：

| 操作 | 耗时 |
| --- | --- |
| MI-GAN 填补（GPU） | **39 ms/帧** |
| 光流 stabilize | **1108 ms/帧** |

光流比填补本身慢 **28 倍**，成为唯一瓶颈。393 帧因此要多花 6 分钟。

**结论**：默认关闭，界面提供可选开关。关闭后逐帧填补本身已足够干净
（笔画能量降幅 95%+）。

## 11. 编码事故：PowerShell 批量替换毁掉 UTF-8

一次真实事故，值得记录。

用 PowerShell 做批量文本替换：

```powershell
(Get-Content webui\app.py -Raw) -replace 'a', 'b' | Set-Content webui\app.py -Encoding UTF8
```

结果：**整个文件的中文全变成乱码**（`鍖哄煙` 这类 GBK 误解码产物），
部分行还被合并。原因是 `Get-Content` 按系统默认编码（GBK）解码了 UTF-8 文件。

**规则：中文文件的批量修改一律用 Python，并用 `encoding="utf-8"` 显式读写。**

```python
p = Path("webui/app.py")
s = p.read_text(encoding="utf-8")
s = s.replace(old, new)
p.write_text(s, encoding="utf-8")
```

恢复过程也记一下：从 git 里的干净版本 `Copy-Item` 回来，再用 Python 脚本
重新应用全部改动，最后做「8 项内容检查 + 无乱码检查」才敢用。

## 12. 可复用的经验

1. **静态叠加水印用时间中位数分离**。这是最有效的单点技巧，比任何颜色/边缘判据都稳。

2. **水印会移动。** 不要假设位置固定。先做时间轴分析（按段求中位数再看），
   确认「在哪些时段、出现在哪些位置」，再决定架构。

3. **颜色判据在有白色物体的背景上必然失效。** 只有在背景纯净时可用。

4. **结构判据（文字排版）比像素统计判据鲁棒得多。** 「两个字高度一致且相邻」
   这个条件在自然画面里几乎不可能偶然成立。

5. **用户可见的变量必须自适应。** @昵称长度、分辨率、视频时长都会变。
   写死任何一个都会在真实使用中出问题。

6. **验证要有对照组。** 只证明「水印没了」不够，还要证明「别的地方没变」。
   否则无法排除「整片糊掉」这种假成功。

7. **半透明叠加物用「区域内结构复杂度」而非颜色来验证。** 药丸就是典型例子。

8. **GPU 老架构要查 compute capability。** 官方 wheel 可能已经不支持，
   必须锁定版本组合，且要同时锁定 ORT 和 cuDNN。

9. **性能优化前先 profile。** 以为是 GAN 慢，实际是光流慢 28 倍。

10. **中文文件不要用 PowerShell 批量替换。**
